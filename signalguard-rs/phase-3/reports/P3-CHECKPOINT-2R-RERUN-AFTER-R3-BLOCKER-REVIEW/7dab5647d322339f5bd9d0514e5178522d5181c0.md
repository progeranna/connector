### `web/src/pages/DashboardPage.tsx`

Verified blob: `7902eaf53c1b4d239627ee438a354176aa2ae750`

The relevant modal ownership state is local to `DashboardTablesGrid`. Symbol Detail identity is `{ mode, symbol, returnContext }`; nested symbol anomaly detail retains a `parentIdentity` of the same shape.

The mode/symbol replacement effect computes `modeChanged` with `previousUiModeRef`, resolves the current Symbol Detail or nested parent identity, replaces the mode when necessary, and then conditionally replaces the symbol only under this guard:

`!modeChanged && selectedSymbol && nextIdentity.symbol !== selectedSymbol`

When replacement occurs, the effect collapses any nested symbol anomaly detail back to `{ type: "symbolDetail", identity: nextIdentity }`, which correctly clears the stale nested anomaly UUID.

`activePopupIdentity` separately replaces only the mode for an already-open `symbolDetail` during render when its mode is stale. It does not replace the symbol.

### `web/src/features/dashboard/selectedSymbol.ts`

Verified blob: `84fd18c12c05f837d021995258bf9252167b17a0`

Selected symbols are stored under per-mode keys (`signalguard:selected-symbol:<mode>`). On a mode render, `useSelectedSymbol` synchronously reads the stored selection for the requested mode when its internal state still belongs to another mode, then resolves that value against available symbols. This independently supports Demo restoring its own stored `BTCUSDT` while Live can separately store `ETHUSDT`.

### `web/src/app/AppShell.tsx`

Mode selection changes only the UI mode; symbol selection updates the selected symbol for the active mode. Therefore header ownership is independently driven by the new mode's resolved selected symbol and is not driven by open popup identity.

## Independent causal reconstruction

The reported browser state is internally consistent with the exact accepted source, and the source provides a deterministic causal path for it.

1. Demo begins with its stored selected symbol `BTCUSDT`; header and popup can both be `demo:BTCUSDT`.
2. Switching to Live while Symbol Detail/nested detail is open sets `modeChanged = true`. The effect replaces `demo` with `live`, skips symbol reconciliation because of `!modeChanged`, and collapses nested detail to Symbol Detail. Because the symbol is still `BTCUSDT`, the state is correct: `live:BTCUSDT`.
3. Selecting `ETHUSDT` while remaining in Live leaves `modeChanged = false`. The effect sees selected symbol `ETHUSDT`, uses `replaceSymbolPopupSymbol`, clears the nested UUID by collapsing to Symbol Detail, and produces `live:ETHUSDT`.
4. Opening a Live ETH anomaly gives nested state whose `parentIdentity` is `live:ETHUSDT`.
5. Switching back to Demo causes both Dashboard/header selected-symbol ownership to resolve against Demo's separate stored key, producing Demo-selected `BTCUSDT`.
6. In the popup effect, however, `modeChanged = true`. Starting from parent identity `live:ETHUSDT`, it replaces only the mode, producing `demo:ETHUSDT`, and skips symbol reconciliation because `!modeChanged` is false.
7. Because the identity changed, the nested Live anomaly UUID is correctly removed and the state becomes Symbol Detail with identity `demo:ETHUSDT`.
8. The state update itself does not change the effect dependencies `[selectedSymbol, selectedUiMode]`; with Demo already resolved to `BTCUSDT`, there is no guaranteed second effect pass that would repair `ETHUSDT` to `BTCUSDT`.
9. The header remains independently owned by Demo's resolved `BTCUSDT`, while Symbol Detail now loads the resource for the internally retained `demo:ETHUSDT` identity.

This exactly explains the reported state without requiring a routing, resource, backend, CSS, favicon, focus, or environmental fault:

- header mode: Demo
- header symbol: `BTCUSDT`
- nested Live anomaly UUID: cleared
- open Symbol Detail parent: `demo:ETHUSDT:symbols`
- modal heading/content: ETHUSDT

The failure is therefore a modal identity reconciliation defect, not a stale network response or late resource resolution defect.

## Checkpoint violation

Accepted: **yes**.

The Checkpoint replacement contract requires stale old mode/symbol identity to disappear immediately and selected-symbol ownership to remain correct with Symbol Detail/nested detail open.

After the Live/ETHUSDT to Demo transition, retaining `ETHUSDT` in the open Symbol Detail while the resolved Demo selection is `BTCUSDT` violates both requirements:

- old symbol identity does not disappear from the open parent;
- the open modal is not owned by the resolved selected symbol of the new mode.

The fact that the nested UUID clears and the old mode changes from Live to Demo is partial correctness, not acceptance.
