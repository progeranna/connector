## Goal

Introduce an explicit DTO-to-view-model boundary for the market-detail data path created by P2-MP02.

The dedicated symbol route and existing popup must render the same explicit market view model rather than formatting, deriving labels, and assembling display values directly from network DTO-shaped objects.

This task is not a visual redesign, not a backend-contract task, and not a general decomposition of the entire dashboard.

## Architectural boundary

### Network DTO boundary remains unchanged

The existing Zod schemas and inferred wire types in:

`web/src/features/dashboard/types.ts`

remain the network-contract boundary for this mini-phase.

Do not change their schemas, optional/null semantics, names, or exports.

The existing query/fetch boundary in:

`web/src/features/dashboard/api.ts`

also remains unchanged.

### New view-model boundary

Create narrowly scoped market-detail model/adapter modules under:

`web/src/features/dashboard/**`

Use names that clearly distinguish wire DTOs from UI-facing models, for example:

- `marketViewModel.ts`;
- `marketAdapters.ts`;
- or an equivalently clear two-module split.

Do not create a generic framework or repository abstraction.

### Adapter ownership

The adapter/view-model layer must own, for the market-detail route and popup:

- DTO/resource-to-view-model conversion;
- canonical identity preservation;
- derived health/status text and tone;
- display formatting decisions currently repeated in presentation;
- null/missing optional-value display representation;
- anomaly display rows or equivalent explicit anomaly view models;
- stable ordering/selection needed for the market-detail presentation;
- protection against combining values from different symbol identities.

Use existing formatting/status helpers where suitable. Do not duplicate existing formatting algorithms without justification.

### Presentation ownership

Route and popup presentation should own only:

- rendering;
- user events;
- loading/error/unavailable/success shell selection;
- layout and accessibility behavior.

Presentation must not:

- join unrelated raw DTO arrays;
- derive a fallback from another symbol;
- invent zeroes for missing values;
- independently implement status-label or display-format logic already represented in the shared view model.

## Required implementation

1. Inspect the exact-base market-detail route, popup resource, shared symbol resource, and their tests.
2. Define explicit readonly UI-facing types for the market-detail success state.
3. Add deterministic pure adapter functions from the existing P2-MP02 resource/DTO boundary to those view models.
4. Preserve `{mode, symbol}` identity in the adapted result.
5. Ensure a DTO/resource with a mismatched symbol cannot be exposed as a view model for another symbol. Preserve existing P2-MP02 identity checks rather than replacing them with looser behavior.
6. Move repeated market-detail display derivation out of `SymbolDetailPage` and the popup path into the adapter/view-model layer where this can be done without changing visual output.
7. Make route and popup consume the same view-model contract for equivalent market identity.
8. Preserve current loading, error, unavailable, empty-anomaly, and success behavior.
9. Preserve selected-symbol persistence, route names, popup return context, and request/query behavior.
10. Keep the change narrowly focused on the market-detail path. Do not decompose unrelated dashboard sections.

## Existing semantics to preserve

- Live detail remains backed by dedicated state, health, and filtered-anomaly resources.
- Demo detail keeps current summary-backed state/health and Demo timeline-owned anomalies until a later explicit contract changes backend availability semantics.
- Dashboard summary remains mode-wide for overview/catalog ownership.
- No Demo data may be used as Live fallback.
- Missing values remain missing/unavailable and must not become numeric zero.
- Route and popup must not disagree for the same successful market identity.
