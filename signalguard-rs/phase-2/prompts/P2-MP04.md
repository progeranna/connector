## Goal

Establish one deterministic checked OpenAPI 3.x contract, or an equivalently precise machine-readable contract only if OpenAPI is technically unsuitable, generated from typed backend contract definitions and validated against the existing frontend boundary.

The result must make drift CI-visible for:

- route paths and HTTP methods;
- path and query parameter names;
- parameter requiredness and allowed values;
- request body fields;
- response property names;
- optional versus nullable semantics;
- enums;
- decimal/string representation;
- date-time representation;
- arrays and nested objects;
- response identity fields.

The checked artifact must be deterministic and reviewable. It must not contain generation timestamps, host-specific paths, random ordering, or environment-dependent values.

## Required contract scope

Cover the current public JSON API used by or relevant to the web console, including at least:

- `GET /health`;
- `GET /runtime/mode`;
- `POST /runtime/mode`;
- `GET /pipeline/health`;
- `GET /dashboard/summary`;
- `GET /symbols`;
- `GET /market/{symbol}/state`;
- `GET /market/{symbol}/health`;
- `GET /market/{symbol}/timeline`;
- `GET /anomalies`.

`GET /metrics` is a Prometheus text endpoint rather than the JSON web-console contract. Either exclude it explicitly in generated contract metadata/tests or document it with its actual text response without pretending it is JSON.

The worker must inspect current handlers/query DTOs and use their actual parameter inventory. Do not infer or invent filters, fields, status codes, or endpoints.

## Contract-source architecture

Use a typed backend source of truth.

Preferred shape:

- schema derives or typed schema definitions live with the backend DTO/query types;
- a narrowly scoped backend contract module assembles endpoint metadata and component schemas;
- route path constants are shared between the router and the contract module where feasible;
- a deterministic exporter writes the checked artifact;
- a check mode regenerates in memory or to a temporary file and fails on byte or semantic drift.

A manually maintained JSON/YAML artifact without a backend generator is forbidden.

A generator that merely copies a second manually duplicated frontend schema is forbidden.

Using a focused schema/OpenAPI dependency is allowed when justified. Keep dependency surface minimal and pin only through normal Cargo resolution. Do not introduce a general framework migration.

## Route-source requirements

`src/api/routes.rs` may change only to replace existing literal paths with shared constants or equivalent contract inventory plumbing.

The route graph, handlers, methods, nesting, middleware, state, and behavior must remain identical.

Add executable backend tests proving the contract route inventory and the Axum route inventory cannot silently diverge. Acceptable proof includes shared path constants plus method/path inventory tests and route probes. Pure source-text substring assertions alone are insufficient as the only proof.

## Backend schema requirements

The generated contract must accurately describe current serialization, including:

- Rust `Option<T>` fields that serialize as JSON `null` when present must be nullable;
- truly optional request/query fields must not be marked required;
- required response properties must remain required even when nullable;
- decimal values must match actual JSON serialization consumed by the frontend;
- UUID and date-time formats must be represented accurately;
- mode, status, severity, and other enums must match actual serialized values;
- path symbol and response symbol identity fields must be explicit;
- additional backend fields accepted by current frontend Zod parsing must not be removed from the backend contract merely because the frontend ignores them.

Do not change runtime serialization to make schema generation easier.

## Frontend compatibility validation

Add an executable frontend compatibility test that reads the checked contract artifact and validates the current Zod/network boundary against it.

The test must cover at least:

1. endpoint path and method inventory used by `api.ts`;
2. exact `mode` and `symbol` parameter names and placement;
3. optional `mode` semantics and `demo|live` enum where applicable;
4. required path symbol semantics;
5. dashboard summary field names and nullable nested `state`/`health`;
6. market state subset consumed by the frontend, including decimal strings and nullable values;
7. market health fields and status enum;
8. timeline symbol, points, anomalies, nullable metrics, and date-time fields;
9. anomaly response fields, severity enum, and nullable observed/threshold values;
10. runtime mode response/request fields used by the frontend or operator UI;
11. additive backend fields remaining compatible with Zod object parsing;
12. failure when a fixture mutates a parameter name, nullability, enum, or required property.

The test must inspect the machine-readable artifact, not duplicate the expected contract as a second full object literal.

This mini-phase validates compatibility; it does not replace `web/src/features/dashboard/types.ts` with generated types.
