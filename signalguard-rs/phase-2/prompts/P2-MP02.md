## Goal

Make symbol-detail resources explicitly owned by canonical market identity instead of deriving symbol detail primarily by filtering a broad dashboard summary.

The route and popup must request and render data using the same server-resource identity:

- runtime mode;
- canonical `SymbolId`;
- resource family;
- any existing server-side filter that changes returned data.

Presentation state such as route versus popup, open versus closed, or selected tab must not become part of server-resource identity unless it changes the server response.

## Required implementation

Inspect the exact base and centralize/adopt dedicated TanStack Query hooks for the existing symbol-addressable backend resources that are actually consumed by the symbol detail route or popup.

At minimum, evaluate and, where the exact-base backend already exposes and the UI consumes them, implement dedicated symbol-owned queries for:

- latest market state;
- market health;
- market timeline;
- symbol-filtered anomalies.

Do not invent a backend endpoint. Reuse the exact existing HTTP contract, query parameters, schemas, `fetchJson` boundary, `AbortSignal` behavior, and refresh policy.

The broad dashboard summary may remain the source for dashboard-wide overview data, catalog population, aggregate counts, and other genuinely mode-wide resources. It must no longer be the primary source from which route/popup symbol detail is filtered when a dedicated endpoint already exists.

Extend the centralized query-key module introduced by P2-MP01 for every dedicated resource introduced or adopted here.

Preserve compatibility exports where existing consumers or tests require them.

## Request-identity requirements

Executable tests must prove all applicable invariants:

1. Demo and Live identities differ for every mode-sensitive symbol resource.
2. BTCUSDT and ETHUSDT identities differ for every symbol-owned resource.
3. State, health, timeline, and anomaly resource families cannot alias one another.
4. Equal canonical inputs produce structurally equal stable serializable keys.
5. Symbol input passes through the existing canonical `SymbolId` boundary.
6. Case and surrounding whitespace normalize consistently.
7. Absent or invalid symbols retain an explicit disabled-query identity and never alias a valid symbol.
8. Route and popup for the same mode/symbol/resource share the same server-resource key.
9. Popup-open state and other presentation-only state are excluded from server-resource keys.
10. Every existing server-side parameter that changes returned data appears in the query key.
11. A resource for a newly selected symbol cannot render the previous symbol's data as if it belonged to the new identity.

Use readonly serializable tuples or an equivalently stable structure.

## UI ownership and switching behavior

Preserve both interaction surfaces:

- dedicated symbol route;
- existing symbol detail popup.

The route and popup may share hooks and cache entries for the same canonical resource identity.

When mode or symbol changes:

- do not relabel previous-symbol data as current-symbol data;
- do not synthesize Demo data for Live;
- do not convert missing/loading/error state into zero-valued market data;
- preserve the existing route and popup shell while the new resource is loading;
- maintain cancellation through TanStack Query's `AbortSignal` path;
- avoid timer-based race tests when controlled deferred promises can prove behavior deterministically.

If exact-base UX intentionally keeps previous data visible during refetch, it must remain visibly associated with its original identity and must not appear under the newly selected symbol label. Prefer existing product behavior unless it violates the no-cross-symbol invariant.
