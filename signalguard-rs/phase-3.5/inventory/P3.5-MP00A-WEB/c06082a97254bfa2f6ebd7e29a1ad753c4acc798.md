### 4.2 Shared root-layout qualification

`ConsoleLayout` statically imports `AppShell`. `AppShell` statically imports and renders `GlobalMarketTicker`, and both use dashboard query/state modules. Consequently, route splitting cannot be assumed to remove all dashboard-domain code, TanStack Query, or Zod from the base application graph. The root header and ticker keep a shared dashboard API/schema chain eager.

The symbol-detail route also shares substantial code with dashboard popups: `DashboardPage` already imports the market adapter, symbol-resource path, and shared symbol-detail presentation modules. Lazy-loading only `/symbols/:symbol` therefore cannot be assumed to isolate that entire feature chain.

## 7. Exact local experiment for Recharts inclusion and contribution

A later local worker should perform two complementary checks in an isolated, disposable worktree:

1. **Rollup module-survival audit.** Temporarily add an analysis-only Vite/Rollup `generateBundle` hook, without committing it, that records every output chunk’s `chunk.modules` keys, `renderedLength`, `renderedExports`, and `removedExports`. Group module IDs under `node_modules/recharts/` and its surviving transitive dependencies. This proves which modules survive the named import and in which emitted assets they appear. `renderedLength` is module attribution evidence, not final gzip attribution.
2. **Controlled final-asset delta.** Build the unchanged baseline, then a temporary variant that replaces only the Recharts-backed chart renderer with an API-compatible inert renderer while preserving the Timeline shell, query ownership, normalization, and state branches. Compare every final raw and gzip JS asset. Treat the delta as an upper bound for the complete chart-renderer/Recharts chain, not as a pure Recharts-only byte count, because minification and cross-module tree-shaking can alter surrounding output.

Do not infer full tree-shaking from the named syntax alone. Do not use a subpath-import variant unless the installed Recharts package exports that subpath and the variant is separately typechecked and built.

## 9. Bundle-checker semantics

`web/scripts/check-bundle-size.mjs`:

1. reads `web/bundle-size-budget.json`;
2. recursively walks `dist/assets`;
3. accepts every regular file ending in `.js`, `.mjs`, or `.cjs`, case-insensitively;
4. records raw filesystem byte size with `lstat`;
5. defines **largest JS** as the maximum raw size of one collected JS asset;
6. defines **total JS** as the raw sum of all collected JS assets;
7. fails only when a value is strictly greater than its budget.

Therefore:

- `maxLargestJsBytes` controls the largest individual emitted JS asset.
- `maxTotalJsBytes` controls the sum of every emitted JS asset under `dist/assets`.
- Lazy chunks still count toward total JS.
- Equality with either budget passes, but the accepted baseline equals both limits and therefore has zero raw-byte headroom.
- Code splitting can reduce the largest asset while total JS remains similar or rises because code is redistributed and dynamic-loader/wrapper or cross-chunk effects may be introduced. The exact result is a build hypothesis.
- With the current total limit equal to the baseline, any positive total-JS increase would fail even if the largest asset becomes smaller.
- Total JS alone is insufficient for initial-load performance because it does not distinguish the entry/static request graph from later route/chart chunks, does not report request count, and does not enforce gzip transfer cost.

A later MP09-compatible additive metric is **initial entry transitive JS**, reported in raw and gzip bytes from a Vite manifest by recursively following static `imports` from the `src/main.tsx` entry while excluding `dynamicImports`. It can be added without raising or removing the existing largest-JS and total-JS limits. A route-specific initial-load report for `/`, `/dashboard`, `/symbols/:symbol`, and `/anomalies` would further clarify which dynamic chunks are immediately needed per route.

No budget change is proposed or authorized by this audit.

## 12. Required conclusions

1. **Is Recharts statically reachable from the initial entry graph?** Yes. The exact static chain is `index.html -> main.tsx -> App.tsx -> router.tsx -> DashboardPage.tsx -> TimelinePanel.tsx -> recharts`.
2. **Are `/anomalies` and `/symbols/:symbol` eagerly imported?** Yes. `/anomalies` is a direct eager page import; `/symbols/:symbol` is indirectly eager through `CanonicalSymbolRoute`, which statically imports `SymbolDetailPage`.
3. **Would route splitting alone necessarily remove Recharts from `/dashboard`?** No. Splitting only non-dashboard routes has no effect. Lazy DashboardPage breaks the base static edge, but `/dashboard` immediately loads that route module and its static TimelinePanel/Recharts chain. Deferring Recharts within Dashboard requires a separate Timeline/chart boundary.
4. **Can code splitting reduce largest JS without reducing total JS?** Yes. It can redistribute code into smaller assets while total JS stays similar or rises. The exact audited checker counts all lazy chunks toward total.
5. **Which candidate should be tested first locally?** SPLIT-004, specifically the fine-grained Timeline/Recharts chart-renderer boundary, because it directly tests the only chart-specific third-party chain and provides the highest composition information value. This is not implementation authorization.
6. **Which candidate has the lowest semantic regression risk?** SPLIT-001, lazy `/anomalies`, because the page is query-free and has limited route-local behavior. Its likely byte effect is still unknown until built.
7. **Which findings are proven statically versus hypotheses?** Proven: current eager routes, exact entry/Recharts edges, named Recharts import style, root AppShell shared dependency chain, direct importers, and bundle-checker source semantics. Hypotheses: emitted chunks, Recharts/transitive byte contribution, tree-shaking effectiveness, raw/gzip savings, initial-route request effects, cross-chunk duplication, and whether any prototype remains within the unchanged total budget.
