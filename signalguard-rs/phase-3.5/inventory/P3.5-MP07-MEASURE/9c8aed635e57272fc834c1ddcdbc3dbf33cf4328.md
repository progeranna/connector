## Method and evidence boundary

The clean baseline and every prototype were built in fresh restoration states at the exact base. The standard gates used were:

```text
cd web
npm ci
npm run test:run
npm run typecheck
npm run lint
npm run build
npm run bundle:check
```

For each build, a temporary Vite/Rollup `generateBundle` hook recorded `chunk.imports`, `chunk.dynamicImports`, `facadeModuleId`, `chunk.modules`, rendered lengths, source-module ownership, transformed-module count, and duplicate ownership. The hook and JSON output were deleted from the product worktree. Final per-asset direct gzip was measured with `gzip -c`, matching the contract’s baseline method.

“Initial-entry” is the transitive closure of entry chunks through static `imports`. “Async-only” is every emitted JS chunk outside that closure. The source-module counts below are product `web/src` modules; the transformed count is the full Rollup/Vite module count.

Headless Chromium 1169 with Playwright 1.52.0 ran production-preview checks for baseline, R1, R2a, R2b, and R3. The browser tests used schema-valid local mock API responses so they measured the emitted production application and browser behavior without depending on a running backend. This is actual browser/runtime evidence, but not backend integration evidence. No pixel screenshot comparison was performed.

## Contract classification and rejected alternatives

- R1, R2a, R2b, and R3 are `INITIAL_ONLY_BENEFIT`: initial raw and gzip improve, but total raw JS increases.
- None is `IMPLEMENTATION_CANDIDATE`, because the unchanged total-JS baseline is `757217` and every prototype is larger.
- R2a is rejected in favor of R2b as the symbol candidate because it has `15` more total raw bytes, while also moving canonical validation behind the loading boundary.
- R1 alone is rejected under current policy because its `+1173` total raw delta leaves only `3466` bytes of total headroom and does not meet the remaining `3553`-byte phase requirement.
- R3 is rejected for implementation despite the best initial reduction because its `+1625` total raw delta leaves `3014` bytes of total headroom and fails total-JS non-regression.
- `DashboardPage` splitting was not performed as a separate product prototype because MP07’s mandatory set was the anomalies route, two symbol alternatives, and their combined accepted route boundaries; splitting the dashboard route would immediately request the eager dashboard/Timeline graph for `/` and `/dashboard` and is not a substitute for MP08’s Timeline/Recharts experiment.
- Timeline/Recharts splitting was explicitly not performed. It belongs exclusively to MP08.
- No budget increase is justified or proposed.

## Recommendation

Under the current Phase 3.5 policy, do not implement route splitting. The evidence-backed recommendation is `NO_ROUTE_SPLIT_IMPLEMENTATION` because every tested boundary improves initial cost only by moving code into async chunks and increases total raw JS.

For a future contract that explicitly reopens an initial-only tradeoff, the preferred symbol design is R2b: keep `CanonicalSymbolRoute` eager and lazy-load only `SymbolDetailPage`. The best combined measured prototype for initial cost is R3, but it is not accepted for implementation under the current total-JS rule.

Future writable paths, if separately authorized, are exactly:

```text
web/src/app/router.tsx
web/src/app/CanonicalSymbolRoute.tsx
web/src/app/router.test.tsx
```

Future tests must retain or add:

1. awaited deterministic loading-boundary assertions for `/anomalies` and `/symbols/:symbol`;
2. canonical lowercase/noncanonical redirect coverage and invalid-symbol direct deep-link/refresh coverage;
3. valid BTCUSDT and ETHUSDT deep-link and browser-history coverage;
4. `(uiMode, symbol)` resource identity, Demo/Live isolation, selected-symbol persistence, and no-fallback assertions in `SymbolDetailPage.test.tsx` and `marketNavigationIsolation.test.tsx`;
5. root `ConsoleLayout`, `AppShell`, `GlobalMarketTicker`, and shared provider/query ownership guards;
6. dynamic-import failure behavior as a separate route/chunk error test before production implementation.

Implement sequentially if policy changes: measure/validate R2b first, then R1, then the combined graph. This preserves attribution and makes loading UX review explicit. Known tradeoffs are a direct-navigation loading frame and delayed invalid-symbol rendering for R2b. No result depends on an MP09 policy change; MP09 could change acceptance policy, but cannot turn these measured total-JS increases into a total-JS reduction.

MP07 does not help the remaining `3553`-byte total-headroom requirement. The best combined R3 leaves `3014` bytes, which is `539` short of that target.

## Interaction with accepted MP08 C2 measurement

The accepted MP08 C2 result reduces initial JS but increases total raw JS by `852` bytes. Adding that result to R3 would produce:

```text
R3 + MP08 C2 total raw = 758842 + 852 = 759694 bytes
R3 + MP08 C2 total delta = +2477 bytes versus 757217
remaining total budget headroom = 761856 - 759694 = 2162 bytes
```

Therefore a combined MP07 + MP08 implementation could fit under the unchanged absolute budget in this arithmetic (`759694 < 761856`), but it could not preserve total-JS non-regression. Adding C2 to the lower-overhead future-only R2b shape would be `759414` bytes and still be `+2197` versus baseline. The current policy therefore rejects both combined implementations even though the budget would not yet fail.
